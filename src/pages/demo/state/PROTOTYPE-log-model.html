Throwaway prototype — not production code

Does the Decision Log model survive delete, persistence and custom Areas?

Press the buttons. Watch the panel on the right. The point is to find the moment where you say “wait, that shouldn’t be possible.”

The question. The Log today holds a fixed set of four Areas, never deletes a Decision, and keeps nothing after a refresh. We want to add per-machine persistence, delete (one Decision and all of them), and Areas the user can add. Three things collide:

Persistence is not here to make the demo smoother. It is here so someone can keep a Log that is actually worth something to them. That raises the stakes on everything else:

1. A Change points at a Decision by id. Delete the Decision and that Change dangles.
2. “Reset demo” means “refresh and the seed comes back”. Once a Log is someone’s real work, a refresh must never do that.
3. If a user removes an Area that Decisions still sit in, what Area are those Decisions in?

This prototype proposes three answers — snapshot Undo, a saved Log that outranks the seed, and Areas derived from the Decisions themselves — and lets you try to break them.

What this prototype is arguing

Undo is a snapshot, not an inverse. The Log today hands back a change id so undoStatus can take that one Change out again. Every new action would need its own inverse, and “delete every Decision” has an expensive one. Keeping the previous whole state instead costs a few kilobytes and makes every action undoable the same way.

Deleting is removal, not destruction, until the Undo expires. A deleted Decision takes its Changes with it. Nothing dangles, because nothing is left behind pointing at it.

The Area list is derived. An Area is a string on a Decision. The list the filters and the form show is every Area in use, plus any the user added that nothing uses yet. Removing an Area only stops suggesting it: an Area a Decision still sits in cannot disappear, so a Decision is never in an Area that does not exist.

What this prototype found that reading the code did not. Derivation has a floor problem. Delete every Decision and there are no Areas left, so the form has nothing to pick and the Log cannot be added to — the person is trapped the moment Undo expires. So the Area control has to be a field you can type into, not a list you choose from. That also collapses two features into one: you add an Area by using it, and “Add Area” needs no separate screen at all.

Their Log outranks the seed. The save records whether anyone put their own Decisions into it. A Log nobody touched is still just the demo, so a deploy refreshes it. The moment someone records one Decision of their own the Log is theirs, and no deploy may touch it again. Reset demo stays the one door back to the seed, and it clears the save as well as the state, so it still means what it says.
